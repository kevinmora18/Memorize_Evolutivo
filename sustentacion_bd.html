🔗 Cómo se relacionan (con ejemplos reales)

1:1 — uno a uno 4 casos

Columna UNIQUE: users ⇄ player_stats, inventories, user_settings, user_currency. Ej: kevin tiene exactamente 1 settings y 1 currency.

1:N — uno a muchos mayoría

FK repetible: users → matches (evidencia.backend y su partida de 1250 pts), → admin_logs (3 acciones), rooms → room_players.

N:N — muchos a muchos 5 casos

Tabla puente: usuarios⇄logros (user_achievements), usuarios⇄salas (room_players), usuario⇄usuario (friendships).

Sin relación 2 tablas

announcements y promotions son globales: no dependen de ningún usuario, son para todos.

🗺️ DER completo (25 tablas)

PK = llave primaria · UQ = única · FK → tabla referenciada · ⚡ = tabla con trigger.

2️⃣ ACID — evidencias en memorize

A
Atomicidad

Transacción de 2 INSERTs: falló el 2.º (FK) → ROLLBACK total, 0 filas parciales.

C
Consistencia

25 PK + 11 UNIQUE + 26 FK + 149 CHECK rechazan datos malos solos.

I
Aislamiento

Nivel read committed: cada transacción solo ve datos confirmados.

D
Durabilidad

wal_level=replica + fsync=on: lo confirmado sobrevive a caídas.

💡 Idea para exponer: “Si una operación falla a la mitad, PostgreSQL deshace todo; y los 211 constraints impiden guardar datos incoherentes.”

🅰️ Atomicidad — código ejecutado en vivo

Dos operaciones en una transacción: la 1.ª válida (partida + XP del trigger), la 2.ª con usuario fantasma.

BEGIN;
CALL sp_register_match('59f90123-...','classic',200,true,1,90,6,100);
-- CALL OK: partida insertada y trigger sumó XP temporalmente
CALL sp_register_match('USUARIO-FANTASMA','classic',100,true,1,90,5,100);
-- ERROR: sp_register_match: usuario USUARIO-FANTASMA no existe
COMMIT;   -- jamás se ejecuta: la sesión aborta y hace ROLLBACK
-- verificación posterior: kevin intacto
SELECT count(*) FROM matches WHERE "userId"='59f90123-...';  --> 0
SELECT xp, coins FROM users WHERE id='59f90123-...';         --> 0 | 500

💡 Ni la partida válida ni el XP del trigger sobrevivieron: todo o nada, sin filas a medias.

🅲 Consistencia — 4 rechazos ejecutados en vivo

Intentamos guardar 4 datos malos. La BD los rechazó sola, sin código extra:

-- 1. Modo de juego inventado  -->  ERROR: viola chk_game_mode
INSERT INTO game_sessions ("userId","gameMode","timePlayed",result)
VALUES ('...kevin...','modo-inventado',60,'won');

-- 2. Partida de usuario inexistente  -->  ERROR: viola matches_userId_fkey
INSERT INTO matches (id,"userId",mode,score)
VALUES ('TEST-FK-1','USUARIO-FANTASMA','classic',100);

-- 3. Email duplicado  -->  ERROR: viola users_email_key
INSERT INTO users (id,email,"updatedAt") VALUES ('X','kevinmora2838@gmail.com',NOW());

-- 4. Partida sin puntaje  -->  ERROR: score viola NOT NULL
INSERT INTO matches (id,"userId",mode) VALUES ('TEST-NN-1','...kevin...','classic');

💡 Escudo de 211 reglas: 25 PK + 11 UNIQUE + 26 FK + 149 CHECK. El programador puede equivocarse; la BD, no.

🅸 Aislamiento — 2 sesiones reales al mismo tiempo

Sesión A abre una transacción y sube monedas sin confirmar. Sesión B consulta en ese instante:

-- SESIÓN A (queda abierta 12 segundos, SIN commit):
BEGIN;
UPDATE users SET coins = coins + 999 WHERE id = '...kevin...';  -- UPDATE 1

-- SESIÓN B (en paralelo, ve la tabla):
SELECT coins FROM users WHERE id = '...kevin...';  -->  500  ✅ valor VIEJO
-- No ve el +999: lo no confirmado es invisible (read committed)

-- SESIÓN A finalmente: ROLLBACK;
SELECT coins FROM users WHERE id = '...kevin...';  -->  500  (como si nada pasó)

💡 Dos jugadores a la vez nunca ven datos a medias del otro. Demo hecha con 2 conexiones simultáneas reales.

🅳 Durabilidad — lo confirmado sobrevive

SHOW wal_level;  -->  replica   (cada cambio se escribe al diario WAL)
SHOW fsync;      -->  on        (el disco confirma antes de responder OK)
  • WAL (Write-Ahead Log): PostgreSQL escribe cada COMMIT en el diario antes de decir “listo”. Si se apaga el PC, al prender replay del diario y todo confirmado sigue ahí.
  • fsync=on: el sistema operativo no miente: el dato está físicamente en disco.
  • 2.ª capa: backups memorize_backup_antes_mejoras.dump (23 KB) y despues_mejoras.dump (83 KB) en backups/.

💡 Regla de oro: lo que pgAdmin te confirma con COMMIT ya es inmortal: está en disco + en backup.

🎮 A + código — ¿dónde está la atomicidad del juego?

Al terminar una partida, UserService.recordGamePlayed debe guardar dos cosas juntas (usuario + stats):

// backend/src/services/UserService.ts:188-195
const [updatedUser, updatedStats] = await Promise.all([
  this.userRepository.update(userId, { xp, level, coins }),
  this.statsRepository.update(stats.id, stats.toJSON()),
]);
  • ⚠️ Ojo crítico: el código NO usa transacción — si la 2.ª escritura falla, la 1.ª ya quedó guardada.
  • ✅ Por eso la atomicidad real vive en la BD: CALL sp_register_match(...) mete el INSERT + el trigger en una sola transacción implícita (demo: ROLLBACK total).

💡 Frase: “El juego pide, la base de datos garantiza: o se guarda todo, o no se guarda nada.”

🎮 C + código — doble capa de validación

Capa 1 — el backend rechaza lo malo antes de tocar la BD:

// backend/src/controllers/UserController.ts:122-125
if (score === undefined || won === undefined) {
  res.status(400).json({ error: 'Datos incompletos' }); return;
}
// backend/src/services/UserService.ts:164-166 -> 'Usuario no encontrado' => 404

Capa 2 — la BD, por si algo se cuela: 211 constraints (el modo inventado, el email duplicado y el score nulo del demo fueron rechazados aquí).

💡 Frase: “El backend filtra y la BD sentencia: dos muros antes del dato sucio.”

🎮 I + código — dos jugadores a la vez

Dos partidas terminan al mismo tiempo → dos prisma.user.update() concurrentes. Con read committed ninguno ve datos a medias (demo: sesión B vio 500).

Y para sumar monedas, el admin usa incremento atómico:

// backend/src/routes/admin.ts:691-696
if (coins) {
  updateData.coins = { increment: coins };  // suma en el servidor, no en memoria
}

💡 Frase: “Ni 100 admins dando monedas a la vez pierden una sola: el incremento ocurre dentro de la BD, bajo aislamiento.”

🎮 D + código — cada await es una promesa en disco

// backend/src/repositories/UserRepository.ts:86-99
const user = await this.prisma.user.update({
  where: { id }, data: { ..., updatedAt: new Date() },
});  // al resolverse el await, el COMMIT ya está en WAL (replica + fsync)
  • Cada escritura deja updatedAt fresco: rastro temporal de cuándo se confirmó.
  • Si el servidor cae un segundo después del await, al reiniciar el WAL repone el dato.
  • 2.ª capa: dumps de 23 KB (antes) y 83 KB (después) en backups/.

💡 Frase: “Await resuelto = dato inmortal: está en disco y en backup.”

3️⃣ CAP — memorize es un sistema CA

  • Consistencia ✅ — un solo nodo: cada lectura devuelve el dato más reciente, sin réplicas desactualizadas
  • Aisponibilidad ✅ — el servidor local responde a cada petición (pg_stat_replication vacío lo confirma: nada que sincronizar)
  • Partición ➖ — no aplica: sin nodos distribuidos no hay red que pueda partirse

📍 Dónde se aplica en Memorize (evidencia del sistema real):

                                              localhost:5432 / memorize
                                              0 réplicas, 0 nodos extra
-- El backend conoce UN solo servidor (sin réplicas de lectura):
// backend/prisma/schema.prisma:5-7
datasource db { provider = "postgresql"  url = env("DATABASE_URL") }
// backend/.env  (contraseña oculta)
DATABASE_URL="postgresql://postgres:****@localhost:5432/memorize"

-- Y el servidor confirma que no tiene con quién partirse:
SELECT count(*) AS replicas FROM pg_stat_replication;  -->  0
  • C se aplica aquí: cada prisma.user.findUnique() y cada vista va al mismo nodo → imposible leer un dato viejo de otra réplica.
  • A se aplica aquí: ese nodo local responde siempre (endpoint /health + test-connection.js OK).

💡 Idea para exponer: “Muestro el .env y el datasource: hay un solo host y cero réplicas. Sin red entre nodos no hay partición posible, así que por diseño el sistema es CA.”

5️⃣ Las 4 vistas ✅ consultas guardadas que se usan como tablas

  • v_ranking_global — ranking con ROW_NUMBER() por puntaje total; excluye baneados
  • v_historial_partidas — cada partida con username y email, ordenada por fecha
  • v_inventario_jugador — equipos, conteos (array_length) y stats; aquí se ve que kevin no tiene inventario
  • v_auditoria_admin — cada log con el admin que actuó y el usuario afectado
SELECT * FROM v_ranking_global;   -- 3 filas: evidencia.backend 1250, rival 1250, kevin 0

6️⃣ Los 2 procedimientos ✅ rutinas que se llaman con CALL

  • sp_register_match(usuario, modo, puntaje, ganó, …) — inserta la partida; el trigger hace el resto (stats, XP, monedas)
  • sp_give_currency(admin, destino, coins, gems, detalle) — premia y deja rastro en admin_logs; rechaza IDs inexistentes con RAISE EXCEPTION
CALL sp_register_match('uuid-kevin','classic',200,true,1,90,6,100);
-- efecto: stats 1/1/200/200/6, xp +20, coins +10 (verificado con ROLLBACK)
CALL sp_give_currency('uuid-admin','uuid-kevin',50,5,'bono');

Encapsulan reglas de negocio dentro de la BD: el backend solo las invoca.

7️⃣ Triggers ✅ requisito: 1 · tenemos 4

Anatomía: CUÁNDO (AFTER INSERT/UPDATE) + DÓNDE (ON tabla) + QUÉ (EXECUTE FUNCTION).

CREATE TRIGGER trg_matches_update_stats
AFTER INSERT ON matches FOR EACH ROW
EXECUTE FUNCTION fn_trg_matches_update_stats();
  • trg_users_auto_create → nace un usuario, nacen su stats + inventario ⭐ empieza por este
  • trg_matches_update_stats → partida guardada, stats y recompensas al día
  • trg_user_achievements_reward → logro completado: +XP y notificación (probado: xp 0→100)
  • trg_boss_reward → boss derrotado: +XP y aviso (probado: +200 XP)
