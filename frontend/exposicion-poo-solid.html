Contexto

¿Qué es Memorize Evolutivo?

Un juego de memoria con modos de juego (Clásico, Tríadas, Bosses, Infinito, Multijugador…), salas en tiempo real por Socket.IO y un motor de juego autoritativo en el servidor. El código está organizado en capas con POO explícita.

Estructura del backend (módulo Multijugador + Motor)
backend/src/
├── Container.ts      ← inyección de dependencias (DI)
├── core/           ← clases base y contratos
│   ├── BaseEntity.ts / BaseService.ts
│   ├── BaseRepository.ts / BaseController.ts
│   └── interfaces/ (IRepository, IServices, IGameModeStrategy)
├── models/

Parte I · Programación Orientada a Objetos

Los 4 Pilares de la POO

La POO modela el mundo real como objetos con estado (propiedades) y comportamiento (métodos). Cuatro pilares la sostienen:

🎭

Abstracción

Modelar solo lo esencial, ocultando la complejidad.

🔒

Encapsulamiento

Proteger el estado interno y exponer una API pública.

🧬

Herencia

Reutilizar comportamiento a partir de una clase base.

🔀

Polimorfismo

Un mismo contrato, muchas implementaciones.

En TypeScript se aplican con interfaces, miembros privados, extends e implements. Veamos cada uno en el código del backend.

PILAR 1 · Backend & Sockets

🔒 Encapsulamiento

SocketManager y GameRoom protegen su estado interno con miembros privados e invariantes de negocio. El cliente de red nunca puede mutar las salas ni las cartas directamente.

backend/src/models/domain/GameRoom.model.ts & SocketManager.ts
export class GameRoom extends BaseEntity<any> {
  private players: Map<string, Player>;      // 👈 estado interno protegido
  private gameState: IGameState;              // 👈 no accesible desde fuera

  // Invariante: solo se voltea si es tu turno y no superas el límite
  public flipCard(playerId: string, cardIndex: number): void {
    if (this.gameState.currentTurn !== playerId) throw new Error('No es tu turno');
    const required = this.getRequiredFlipsCount();
    if (this.gameState.flippedCards.length >= required) throw new Error('Límite alcanzado');
    this.gameState.flippedCards.push(cardIndex);
  }
}
  • Estado interno oculto: en GameRoom, players y gameState son private; en GameEngine lo son turnTimer, evaluating y pendingResolve. Nada se muta desde fuera.
  • Validación de reglas en el dominio: cuando el socket recibe game:flip-card, no hace un push directo; invoca room.flipCard() que valida turnos.
  • Lectura segura por copia: room.getGameState() devuelve una copia superficial ({ ...this.gameState }) para evitar mutaciones externas involuntarias.
PILAR 2 · Backend & Sockets

🎭 Abstracción

Definir contratos e interfaces que aíslan la comunicación en tiempo real de los detalles de almacenamiento o base de datos. SocketManager solo conoce el qué, no el cómo.

backend/src/core/interfaces/IServices.ts — el contrato
export interface IRoomManager {
  getRoom(roomId: string): GameRoom | undefined;
  joinRoom(roomId: string, player: IPlayer): GameRoom;
  leaveRoom(roomId: string, playerId: string): void;
  deleteRoom(roomId: string): boolean;
}
backend/src/socket/SocketManager.ts — uso de los contratos
export class SocketManager {
  // Depende de ABSTRACCIONES, no de las clases concretas
  private roomManager: IRoomManager;
  private matchService: IMatchService;
  private engine: GameEngine;

  constructor(io: Server, roomManager: IRoomManager, matchService: IMatchService) {
    this.roomManager = roomManager;
    this.engine = new GameEngine(roomManager, o => this.applyOutcome(o));
  }
}
  • Desacoplamiento total: a SocketManager no le interesa si las salas residen en un Map en RAM, en Redis o en PostgreSQL; solo invoca this.roomManager.getRoom(id).
  • Abstracción de seguridad: authenticateHandshake abstrae la verificación criptográfica del token JWT sin contaminar la lógica de eventos del juego.
  • Testeabilidad inmediata: al depender de IRoomManager, podemos testear los sockets con un Mock sin levantar base de datos ni servidores complejos.
PILAR 3 · Backend & Sockets

🧬 Herencia

Reutilizar comportamiento de identidad y ciclo de vida mediante extends. GameRoom hereda de BaseEntity, unificando la auditoría de todas las entidades del sistema.

backend/src/core/BaseEntity.ts ➔ backend/src/models/domain/GameRoom.model.ts
// 1. Clase base abstracta que centraliza identidad y timestamps
export abstract class BaseEntity<TData = any> {
  readonly id: string;
  readonly createdAt: Date;
  protected _updatedAt?: Date;

  constructor(id: string, createdAt = new Date(), updatedAt?: Date) { ... }
  get updatedAt(): Date | undefined { return this._updatedAt; }
  protected touch(): void { this._updatedAt = new Date(); }

  abstract toJSON(): TData; // 👈 contrato que cada entidad implementa
}

// 2. GameRoom reutiliza la base mediante Herencia
export class GameRoom extends BaseEntity<any> {
  constructor(data: IGameRoomData) {
    super(data.id, data.createdAt); // 👈 reutiliza el constructor padre
  }
}
  • Reutilización de código: GameRoom, User y Match heredan automáticamente id, createdAt y updatedAt sin duplicar código en cada archivo.
  • Jerarquía de Estrategias: los modos de juego (PairsModeStrategy, TriadsModeStrategy) heredan el algoritmo base de match y XP de BaseGameModeStrategy.
PILAR 4 · Backend & Sockets

🔀 Polimorfismo

El motor consulta room.getRequiredFlipsCount() y room.checkMatch() sin saber qué modo está activo: cada estrategia responde distinto (2 cartas en Clásico, 3 en Tríadas, bonus en Boss…). Ni un solo if/switch.

backend/src/engine/GameEngine.ts & backend/src/models/domain/GameRoom.model.ts
// GameEngine NO sabe cuántas cartas se requieren (¿2 en Clásico? ¿3 en Tríadas?)
const required = room.getRequiredFlipsCount(); // 👈 Polimórfico
if (state.flippedCards.length >= required) {
  this.scheduleResolve(room); // resuelve la mano en el servidor
}

// resolveTurn(): delega en la estrategia activa (PairsModeStrategy o TriadsModeStrategy)
const { isMatch, cardIndexes } = room.checkMatch();
if (isMatch) {
  room.registerMatch(handOwner, cardIndexes);
}

Estrategia Clásica (Pairs)

requiredFlips = 2 · Evalúa coincidencias de 2 cartas y otorga 50 XP base.

Estrategia Tríadas (Triads)

requiredFlips = 3 · Evalúa coincidencia de 3 cartas idénticas y otorga 75 XP base.

Principio Open/Closed (OCP): Si agregamos un modo de 4 cartas (Cuartetos), solo creamos una estrategia nueva y la registramos; no tocamos GameEngine ni GameRoom.

MOTOR DE JUEGO · backend/src/engine

⚙️ Los 4 Pilares en el Motor (server-authoritative)

El motor (GameEngine, RoomCommandHandler, GameRoom, TurnTimer, DeckGenerator) concentra las reglas y aplica los 4 pilares sin acoplarse a Socket.IO:

🔒

Encapsulamiento

GameEngine guarda turnTimer, evaluating y pendingResolve como private; nadie muta el turno desde fuera.

GameEngine privados
🎭

Abstracción

El motor depende de IRoomManager y de un callback onOutcome; no conoce SocketManager ni la base de datos.

RoomCommandHandler
🧬

Herencia

GameRoom extends BaseEntity reutilizando identidad y timestamps; TurnTimer encapsula el reloj de turno.

BaseEntity <|-- GameRoom
🔀

Polimorfismo

room.getRequiredFlipsCount() y checkMatch() delegan en IGameModeStrategy (2 vs 3 cartas) sin if/switch.

Strategy polimórfica
backend/src/engine/GameEngine.ts — el motor emite resultados abstractos, no eventos de Socket.IO
// Contrato de salida del motor: qué pasó, no cómo se transmite
export interface CommandOutcome { type: string; room?: GameRoom; payload?: any; }

// El command handler valida y aplica la jugada sobre el dominio
const room = this.roomManager.getRoom(roomId);
room.flipCard(userId, cardIndex); // ← GameRoom valida turno y cartas volteadas

// Y el transporte (SocketManager) es quien traduce el outcome a eventos
private applyOutcome(o: CommandOutcome): void { ... }
Parte II · Principios SOLID

SOLID

Los 5 principios de diseño (Robert C. Martin) que hacen el software fácil de mantener, extender y probar. Las siglas:

S

Single Responsibility

Responsabilidad Única

O

Open / Closed

Abierto a extensión, cerrado a modificación

L

Liskov Substitution

Sustitución de Liskov

I

Interface Segregation

Segregación de interfaces

D

Dependency Inversion

Inversión de dependencias

SOLID · S

S — Responsabilidad Única

Cada clase tiene un solo motivo para cambiar. En Memorize Evolutivo, cada servicio tiene una única responsabilidad claramente definida:

🔐

AuthService

Solo autenticación: loginOrRegister(), validateAccess(), isAdmin().

👤

UserService

Solo perfil y progresión: getUserProfile(), addXpToUser(), rewardCoins().

🗄️

repositories/

Solo acceso a datos. Prisma vive aquí, nunca en servicios.

backend/src/services/AuthService.ts — ejemplo real del proyecto
export class AuthService extends BaseService {
  private userRepository: UserRepository;

  // ✅ Responsabilidad: login/registro
  async loginOrRegister(email: string): Promise<User> {
    if (!email || !email.includes('@')) throw new Error('Email inválido');
    
    let user = await this.userRepository.findByEmail(email);
    if (!user) user = await this.userRepository.create({ email });
    
    if (user.isCurrentlyBanned()) throw new Error('Usuario baneado');
    return user;
  }

  // ✅ Responsabilidad: validar acceso
  async validateAccess(userId: string): Promise<boolean> {
    const user = await this.userRepository.findById(userId);
    return user ? !user.isCurrentlyBanned() : false;
  }
}

Refactor Admin: AdminService (1 clase haciendo todo) → AdminUserService + AdminContentService + AdminAnalyticsService + AuditLogService (4 clases cohesivas). Cada una con 1 razón para cambiar.

SOLID · O

O — Abierto a extensión, cerrado a modificación

Añadir un modo de juego nuevo no obliga a tocar el motor: se crea una estrategia nueva y se registra. El código existente queda cerrado a modificación.

backend/src/models/strategies/GameModeStrategy.ts — Factory extensible
export class GameModeFactory {
  private static strategies = new Map<string, IGameModeStrategy>([
    ['classic', new PairsModeStrategy()],
    ['triads',  new TriadsModeStrategy()],
    ['boss',    new BossModeStrategy()],
    // ... 7 modos en total
  ]);

  static getStrategy(mode: string): IGameModeStrategy { ... }
  static registerStrategy(name: string, s: IGameModeStrategy): void { ... } // ← abierto
}

Nuevo modo = nueva clase + registrar

Crear un modo Cuartetos (4 cartas) es escribir una subclase de BaseGameModeStrategy y registrarla. GameEngine, GameRoom y MatchService no cambian.

Tableros y reglas extensibles

Las 7 estrategias comparten la base y definen solo sus reglas (checkMatch, getRequiredFlipsCount). También los repositorios se sustituyen sin tocar a quien los consume.

SOLID · L

L — Sustitución de Liskov

Cualquier subclase de BaseGameModeStrategy debe poder reemplazar a la base sin romper el motor. El motor solo usa el contrato, nunca el tipo concreto.

backend/src/models/domain/GameRoom.model.ts — estrategia sustituible en runtime
// GameRoom guarda cualquier IGameModeStrategy, no un modo concreto:
private strategy: IGameModeStrategy;

checkMatch() { return this.strategy.checkMatch(this._cards, this.state.flippedIndexes); }
getRequiredFlipsCount() { return this.strategy.getRequiredFlipsCount(); }

// PairsModeStrategy, TriadsModeStrategy, BossModeStrategy... todas cumplen el contrato
backend/src/core/BaseRepository.ts — repositorios intercambiables
// LeaderboardService depende de IUserRepository;
// da igual si detrás está Prisma o un mock de test
const top = await this.userRepository.findTopByField('xp', limit);

// Cualquier IUserRepository válido es un sustituto correcto
  • Estrategias: las 7 subclases respetan el contrato de IGameModeStrategy → el motor las trata a todas igual.
  • Repositorios: UserRepository, InventoryRepository, AnalyticsRepository… son sustituibles tras su interfaz, lo que hace el servicio testeable con dobles.
SOLID · I

I — Segregación de Interfaces

Ningún consumidor debe depender de métodos que no usa. Los repositorios se parten en contratos pequeños y algunos no heredan el CRUD completo.

backend/src/core/interfaces/IRepository.ts — contratos pequeños
export interface IReadRepository<T, ID>  { findById; findAll; }
export interface IWriteRepository<T, ID> { create; update; delete; }
export interface ICrudRepository<T, ID>
  extends IReadRepository<T, ID>, IWriteRepository<T, ID> {}
Solo los métodos que cada repositorio necesita
// Registro de auditoría: solo escribe y consulta
interface IAdminLogRepository { createLog(...); findAll(...); }

// Inventario y salas exponen solo su contrato específico
interface IInventoryRepository { findByUserId; upsert; }
interface IRoomRepository      { persist; findActive; remove; }
  • IRead / IWrite / ICrud: quien solo lee no arrastra delete ni update.
  • Sin jerarquías forzadas: IAdminLogRepository, IInventoryRepository y IRoomRepository no extienden BaseRepository; declaran únicamente lo que usan.
SOLID · D

D — Inversión de Dependencias

Los servicios de alto nivel no deben depender de Prisma ni de clases concretas, sino de interfaces. Todas las dependencias se ensamblan en un único lugar: el Container.

backend/src/Container.ts — inyección por constructor
// LeaderboardService ya NO recibe un PrismaClient
const leaderboardService = new LeaderboardService(
  this.userRepository,   // IUserRepository
  this.statsRepository,  // IPlayerStatsRepository
  this.matchRepository   // IMatchRepository
);

// AdminService es ahora una fachada sobre 4 servicios cohesivos
this.adminService = new AdminService(
  this.adminUserService, this.adminContentService,
  this.adminAnalyticsService, this.auditLogService
);

Antes

LeaderboardService y AdminService importaban e instanciaban PrismaClient directamente.

Después

Dependen de IUserRepository, IPlayerStatsRepository e IAnalyticsRepository. Prisma queda encerrado en repositories/.

Ensamblaje único

Container decide qué implementación concreta se inyecta; cambiar de ORM afectaría solo a los repositorios.

Ni los servicios ni el motor conocen detalles de infraestructura: RoomManager recibe IRoomRepository, SocketManager recibe IRoomManager. Todo depende de abstracciones, y las abstracciones se inyectan.
Impacto en el proyecto

¿Qué logró aplicar POO + SOLID?

🧩

Refactor SRP medible

AdminService pasó de concentrar todo el panel a ser una fachada sobre 4 servicios cohesivos.

🔁

Inversión de dependencias real

LeaderboardService, AdminService y RoomManager ya no crean su propia capa de datos: la reciben por constructor (D).

🛡️

Estado protegido

GameRoom y GameEngine encapsulan turnos, mazo y temporizador: el socket no puede corromper el estado (E).

🧪

Fácil de probar y cambiar

12 tests en Vitest cubren el motor y la evolución. Al depender de interfaces, los servicios se testean con dobles (D, I).

En una frase: los 4 pilares definen cómo se modela el dominio (GameRoom, estrategias, entidades), y SOLID define cómo se conectan las capas para que el juego crezca sin volver el código un laberinto.
Resumen

Mapa del código

Los 4 Pilares

  • Abstracción → IRepository, IServices, IGameModeStrategy (core/interfaces)
  • Encapsulamiento → GameRoom (private players/gameState), GameEngine (turnTimer, evaluating)
  • Herencia → GameRoom extends BaseEntity; BaseService, BaseRepository
  • Polimorfismo → IGameModeStrategy + 7 estrategias vía GameModeFactory

SOLID

  • S → 1 servicio = 1 responsabilidad; AdminService → 4 servicios
  • O → GameModeFactory.registerStrategy() añade modos sin tocar el motor
  • L → las 7 estrategias sustituyen a BaseGameModeStrategy; repos tras su interfaz
  • I → IRead/IWrite/ICrud + IAdminLogRepository/IInventoryRepository/IRoomRepository
  • D → Container inyecta interfaces; servicios sin Prisma, motor sin Socket.IO
